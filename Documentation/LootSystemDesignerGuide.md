# Survival Loot System: Designer Guide

This guide explains how to create and place loot without changing C++ code.

The system has two world-facing forms:

- **Visible loot spawn point:** rolls an item and creates a normal visible `APickup` in the world.
- **Searchable loot container:** stays hidden inside a fridge, cabinet, chest, safe, or similar prop until the player searches it.

Loot is generated by the server. Clients cannot create, duplicate, or claim loot by themselves.

## 1. The mental model

Think of loot as four separate pieces:

1. **Item definition:** what the item is, such as soda, water, or a remedy.
2. **Loot table:** what items are allowed to appear and how likely each item is.
3. **World placement:** where the table is used, such as a kitchen fridge or countertop.
4. **Gameplay Tags:** optional labels that can further filter a table when the project needs more reuse or balancing control.

For the beginner workflow, the assigned loot table is the main source of truth. A fridge table should already contain fridge-appropriate items. Tags are an advanced filter and are not required for every table.

Example:

```text
DA_Loot_Kitchen_Fridge:
    Soda
    Water
    Contaminated Water
```

The fridge can roll soda, water, or contaminated water because those are the entries intentionally placed in its table. Salt belongs in a cabinet table, not in the fridge table.

## 2. Create or verify item definitions

Before creating a loot table, make sure the item already exists as a data asset.

1. Open the Content Browser.
2. Locate the item data asset, usually under `Content/Miscellaneous/DataAsset`.
3. Open it and verify:
   - `Display Name` is set.
   - `Weight` is correct.
   - `Pickup Mesh` is assigned for visible world pickups.
   - Consumable effects are correct if the item is drinkable, edible, or medicinal.
4. Save the asset.

For the current project, existing examples include soda, water, contaminated water, and remedy assets under:

```text
Content/Miscellaneous/DataAsset/Consumables
```

An item does not need a pickup mesh to appear inside a searchable container, but it does need a pickup mesh to look correct as a visible world pickup.

## 3. Create a loot table

1. In the Content Browser, create or open a data-asset folder. Recommended location:

   ```text
   Content/Miscellaneous/DataAsset/LootTables
   ```

2. Right-click in the folder.
3. Choose `Miscellaneous > Data Asset`.
4. Select `SurvivalLootTable`.
5. Name the asset after its purpose, for example:

   ```text
   DA_Loot_Kitchen_Fridge
   DA_Loot_Kitchen_Counter
   DA_Loot_Garage_Shelf
   ```

6. Open the new loot table.
7. Set `Maximum Rolled Items`.
   - Use `1` for a visible spawn point.
   - Use `2` or `3` for a searchable container.
8. Add entries to the `Entries` array.

Beginner rule: only add items that make sense for this table. Do not put every possible item into one table and rely on tags to remove the wrong ones.

Each entry has these fields:

| Field | Meaning |
|---|---|
| `Item Definition` | The item that may be generated. |
| `Required Tags` | Every tag here must exist on the spawn point or container. |
| `Excluded Tags` | If any of these tags exist, this entry is rejected. |
| `Weight` | Relative chance compared with other valid entries. |
| `Minimum Quantity` / `Maximum Quantity` | Number of item instances created when the entry wins. |

### Understanding weight

Weight is relative, not a percentage.

```text
Soda       Weight 5
Water      Weight 3
Remedy     Weight 1
```

Among valid entries, the rough distribution is 5:3:1. The exact result is randomized each time the table is rolled.

The system also has an intentional chance to return no item. A valid loot table is allowed to produce an empty fridge or an empty spawn point.

## 4. Optional advanced filtering with Gameplay Tags

Tags are optional labels that can filter loot-table entries. They are useful when many placements share a broad table or when the project needs location, quality, regional, or event-based variations.

Tags are not required for the basic workflow. If a table is already specific, such as `DA_Loot_Kitchen_Fridge`, simply put the correct items in that table and leave tag fields empty.

Prefer a small, reusable vocabulary over a unique tag for every prop.

Recommended starting taxonomy:

```text
Location.Kitchen
Location.Garage
Location.GasStation

Container.Fridge
Container.Cabinet
Container.Safe
Container.Chest

Loot.Food
Loot.Drink
Loot.Medicine
Loot.Tools
Loot.Ammunition
```

Create tags in `Project Settings > Gameplay Tags`.

Use tags at two levels when advanced filtering is needed:

- **Context tags on the world object:** describe the location and container.
- **Required/excluded tags on a loot entry:** describe what that item needs or cannot use.

Example rules:

```text
Soda:
    Required: Loot.Drink
    Excluded: Location.Garage

Salt:
    Required: Loot.Food, Container.Cabinet

Bandage:
    Required: Loot.Medicine
```

If a tag-filtered table entry never appears, check that every required tag is present and that no excluded tag is present. If tags are making a table difficult to understand, split the table into clearer context-specific tables instead.

## 5. Place a visible loot spawn point

Use a visible spawn point for items that should already be visible in the world, such as soda on a counter or oil on a garage shelf.

1. Compile or open the project in Unreal Editor so the native class is available.
2. In the Place Actors panel, search for `Survival Loot Spawn Point`.
3. Drag the actor into the level.
4. Move and rotate it to the exact location where the pickup should appear.
5. In the Details panel, set:
   - `Context Tags` — the tags that describe this location.
   - `Loot Table` — the table to roll.
   - `Maximum Contents` — normally `1`.
6. Save the level.

Example countertop point:

```text
Context Tags:
    Location.Kitchen
    Loot.Food
    Loot.Drink

Loot Table:
    DA_Loot_Kitchen_Counter

Maximum Contents:
    1
```

The server evaluates the point when the level begins. If the roll succeeds, a normal visible pickup is spawned at the point transform.

### Current visible-point limitation

The current implementation spawns the first rolled item at a visible point. For predictable results, configure visible-point tables with:

```text
Maximum Rolled Items = 1
Minimum Quantity = 1
Maximum Quantity = 1
```

Use searchable containers when you need two or three separate hidden items.

## 6. Demo: build a kitchen loot setup

This is the recommended first exercise for a new designer. It teaches the complete basic workflow without requiring advanced tags.

### Create the tables

Create these three loot tables:

```text
DA_Loot_Kitchen_Fridge
    Soda       Weight 50
    Water      Weight 40
    Contaminated Water  Weight 10

DA_Loot_Kitchen_Cabinet
    Salt       Weight 50
    Canned Food  Weight 35
    Remedy     Weight 15

DA_Loot_Kitchen_Counter
    Soda       Weight 50
    Water      Weight 35
    Canned Food  Weight 15
```

Set the maximum rolled items to `1` for the countertop table. Set the fridge and cabinet tables to `2` or `3` if they will be used by searchable containers.

### Place the actors

1. Place the kitchen static meshes in the level.
2. Place one `Survival Loot Container` inside the fridge.
3. Set its display name to `Fridge`.
4. Assign `DA_Loot_Kitchen_Fridge`.
5. Resize its collision box so the fridge can be targeted naturally.
6. Place one `Survival Loot Container` over each cabinet section the player should search independently.
7. Set each cabinet display name to `Cabinet`.
8. Assign `DA_Loot_Kitchen_Cabinet` to each cabinet container.
9. Place one `Survival Loot Spawn Point` on the countertop.
10. Assign `DA_Loot_Kitchen_Counter` and leave `Maximum Contents` at `1`.

### Test the result

1. Start Play In Editor.
2. Look at the fridge and confirm the prompt says `Search Fridge`.
3. Search it and verify that it produces soda, water, contaminated water, or an empty result.
4. Search each cabinet separately and confirm each cabinet has its own contents.
5. Look at the countertop and confirm a visible pickup appears at the authored spawn point.
6. Store or use the generated item.
7. Search the same container again and confirm it does not reroll immediately.

This demo is the core authoring pattern. Add tags later only when a shared or filtered table solves a real content-authoring problem.

## 7. Place a searchable container

Use a searchable container for a fridge, cabinet, safe, chest, or another prop whose contents should not appear until searched.

1. Add the physical prop to the level.
2. In the Place Actors panel, search for `Survival Loot Container`.
3. Place the container actor over or inside the prop.
4. Set `Container Display Name`, for example:

   ```text
   Fridge
   ```

5. Set `Context Tags`.
6. Assign the `Loot Table`.
7. Set `Maximum Contents` to `2` or `3`.
8. Resize the container's collision box so the player can target it naturally.
9. Save the level.

Example fridge:

```text
Container Display Name:
    Fridge

Context Tags:
    Location.Kitchen
    Container.Fridge
    Loot.Food
    Loot.Drink

Loot Table:
    DA_Loot_Kitchen_Fridge

Maximum Contents:
    3
```

At runtime:

1. The player focuses the actor and sees `Search Fridge`.
2. Searching rolls the table on the server.
3. The player sees `Store Item` and, for consumables, `Use Item` options.
4. If the roll produces nothing, the prompt reports that the fridge is empty.
5. Contents remain the same until they are taken or used.

## 8. Refill behavior

The global refill interval is configured on the survival gameplay data asset:

```text
Content/Miscellaneous/DataAsset/DA_Survival_Gameplay_Data
```

Set:

```text
Loot Recycle Interval Game Seconds
```

The default is `7200` in-game seconds, or two in-game hours.

At each refill evaluation:

- A visible point with an existing pickup is left alone.
- An empty visible point may roll new loot or remain empty.
- A searched container with remaining items is left alone.
- A searched, empty container may roll new loot or remain empty.
- An unsearched container does not generate contents until the player searches it.

The current implementation does not save loot state across a full server restart. Save-game persistence is a later system.

## 9. Designer testing checklist

Before marking a location complete, test the following in Play In Editor:

- The pickup appears at the intended transform.
- The pickup uses the expected mesh and display name.
- The interaction prompt targets the correct actor.
- Searching a container produces zero, one, or multiple valid results.
- Invalid items do not appear because of tag filtering.
- A consumable can be used from the container.
- A stored item appears in the player inventory.
- Searching the same container again does not reroll its contents.
- Empty containers display the empty state.
- A refill does not delete leftover items.

For multiplayer testing, use a listen server or dedicated server and confirm both clients see the same contents.

## 10. Troubleshooting

### Nothing spawns

Check these in order:

1. The spawn point has a loot table assigned.
2. The loot table has at least one valid item definition.
3. The item definition is not invalid or unloaded.
4. The point's context tags satisfy the entry's required tags.
5. The point's context tags do not contain an excluded tag.
6. The table was not allowed to roll empty.

### The item is invisible

The item definition probably has no `Pickup Mesh`. Assign a static mesh to the item definition and test again.

### The player cannot search the container

Check the container's collision box and make sure it blocks the `Visibility` trace channel. Also confirm that the player is within the normal interaction distance.

### A container shows the wrong name

Set `Container Display Name` on the placed `Survival Loot Container` actor. This is the text shown in the interaction prompt.

### The wrong type of item appears

Review the required and excluded tags on the loot-table entry. Context tags are matched as filters; the table does not infer that a prop is a fridge from its mesh name.

## 11. Authoring rules for future designers

- Start with clear context-specific loot tables. Add semantic tags only when they solve a real reuse or filtering problem.
- Use one loot table per meaningful context, not one table per individual point.
- Keep visible points at one item until multi-item visible placement is implemented.
- Keep containers sparse; two or three items is the intended first-pass range.
- Let some valid points roll empty. Empty space is part of the survival-game pacing.
- Do not duplicate the same item definition across many entries unless different weights are intentional.
- Name assets by location and purpose, such as `DA_Loot_GasStation_Fridge`.
- Always test both the lucky roll and the empty-roll case.
